# PranVayu: architecture

Serverless on AWS, region ap-south-1 (Mumbai). Everything the user sees is precomputed; the API only reads.

## 1. Principles

1. **Precompute, then read.** Scheduled jobs fetch, model and store. The API never calls an external source on a user request.
2. **Rules decide, language explains.** Verdicts come from config-driven rules. Any language model only rewrites already-computed facts.
3. **Degrade visibly.** Missing or old inputs lower the confidence label and show a banner. They do not break the page.
4. **Config over code for judgement calls.** Thresholds, weights and the GRAP banner live in versioned config files, not buried in functions.
5. **Replayable.** The same pipeline code runs against archived inputs for the replay and evaluation.

## 2. Component view

```
EventBridge Scheduler
  |-- hourly   --> pv-ingest-fires   --> S3 raw/fires/
  |-- hourly   --> pv-ingest-obs     --> S3 raw/obs/
  |-- 6-hourly --> pv-ingest-winds   --> S3 raw/winds/
  |-- 6-hourly --> pv-ingest-cams    --> S3 raw/cams/
  '-- hourly (+25 min) --> pv-model-run
                              reads S3 raw/*, config/*
                              writes DynamoDB pv-state (LATEST per locality)
                              (P1) calls Strands agent on Bedrock for "why" text
API Gateway (HTTP API) --> pv-api (read-only Lambda)
                              reads DynamoDB pv-state, S3 replay/, S3 evidence/
Amplify Hosting (static SPA) --> calls API Gateway
(P1) Telegram --> API Gateway /telegram --> pv-bot --> DynamoDB pv-subs
(P1) EventBridge Scheduler (evening) --> pv-digest --> Telegram
CloudWatch Logs and metrics for every Lambda
```

## 3. AWS resources

| Resource | Name | Notes |
|---|---|---|
| Lambda (Python 3.12, arm64) | pv-ingest-fires, pv-ingest-obs, pv-ingest-winds, pv-ingest-cams, pv-model-run, pv-api; P1: pv-bot, pv-digest | numpy via the AWS-provided SDK for pandas managed layer if it fits, otherwise a bundled wheel. Verify layer availability in ap-south-1 |
| EventBridge Scheduler | pv-sched-* | Schedules above; one disabled-by-default replay schedule is not needed (replay is a one-off job run from the laptop or a Lambda invoke) |
| S3 | pv-data-<account> | Prefixes: raw/, replay/, evidence/, config-snapshots/ |
| DynamoDB | pv-state, pv-subs (P1) | On-demand billing |
| API Gateway HTTP API | pv-http | Throttling: 20 rps burst, 10 rps steady to start; CORS to the site origin |
| Amplify Hosting | pv-web | Manual zip deploy of the built SPA is enough |
| SSM Parameter Store | /pv/firms_map_key, /pv/openaq_key, /pv/telegram_token | SecureString; read by Lambdas with least-privilege IAM |
| CloudWatch | log groups, 3 alarms | Alarm on model-run errors, ingest failures, API 5xx |
| Bedrock (P1) | Claude via the account's available inference profile | Model access must be enabled; ID chosen in Phase 0 |
| Strands Agents SDK (P1) | in pv-model-run | Open-source; used only for the "why" text |

Eligibility note: deploying on Lambda, API Gateway, DynamoDB, S3 and Amplify already satisfies "deployed on AWS". Strands is optional.

## 4. Pipeline jobs

| Job | Cadence | Reads | Writes | Failure behaviour |
|---|---|---|---|---|
| ingest-fires | hourly | FIRMS area API, 3 VIIRS NRT sources, bbox, 3 days | raw/fires/<ts>.json (deduped detections) | Keep previous file; model-run reports fires age |
| ingest-obs | hourly | OpenAQ latest and hourly values for 12 stations | raw/obs/<ts>.json | Missing station marked null; stale flag after 3 h |
| ingest-winds | every 6 h | Open-Meteo forecast API, 121 grid points | raw/winds/<run>.json | Keep previous; stale flag after 8 h |
| ingest-cams | every 6 h | Open-Meteo air quality API, 12 receptors | raw/cams/<run>.json | As above |
| model-run | hourly | latest raw/*, config/* | DynamoDB LATEST per locality, plus a run log | Per-locality isolation: one failing locality does not block others |

The hourly model-run uses whatever is latest in S3, so ingest jobs can fail independently.

## 5. Storage layout

S3 (bucket pv-data-<account>):
- raw/fires/YYYYMMDDTHHMMZ.json, raw/obs/..., raw/winds/<model>_<runtime>.json, raw/cams/...
- replay/<run_id>/inputs/ (archived inputs), replay/<run_id>/<locality>/<asof>.json (precomputed payloads, one per 3 h)
- evidence/<run_id>/evidence.json (from the evaluation job)
- config-snapshots/<git_sha>/ (copy of config used by each deploy)

DynamoDB pv-state: partition key `pk` = `LOC#<locality_id>`, sort key `sk` = `LATEST`. Attributes: `payload` (JSON), `generated_at`, `schema_version`. One item per locality, under 400 KB.

## 6. Configuration and secrets

Files in `config/` (all versioned; see 05-DATA-CONTRACTS for fields):
- `localities.json`, `model.yaml`, `thresholds.yaml`, `timetable_defaults.json`
- `grap.json` (manual; edited by the team from the latest CAQM order)
- Generated by the evaluation job: `smoke_levels.json`, `bands.json`

Secrets only in SSM Parameter Store. No keys in the repo, the frontend bundle, or logs.

## 8. Stack

- Backend: Python 3.12, numpy, a small HTTP client, pydantic or dataclasses for payload validation, pytest, ruff.
- Frontend: Vite, React, TypeScript, plain CSS with CSS variables (no utility framework, no component kit), Vitest, Playwright for two smoke tests. Hand-built SVG chart. Leaflet or MapLibre only on the smoke detail route (lazy loaded).
- Infra: AWS SAM (open-source SAM CLI), Amplify Hosting.
- Tooling: make or npm scripts for `test`, `lint`, `replay`, `evaluate`, `deploy`.

## 9. Frontend structure

Routes: `/` (answer), `/smoke` (detail), `/evidence`, `/method`. State: locality, language, day, timetable times in localStorage; server data via a single fetch per locality, cached for 5 minutes. Verdicts for edited timetable times are recomputed in the browser from the hourly series in the payload (same rule file shipped to the client as JSON), so editing times needs no network.

Headline and verdict strings are built in the client from i18n dictionaries and payload values. The payload stays language-neutral, except the optional P1 "why" text, which carries `en` and `hi`.

## 10. Observability

- Structured JSON logs with run id, locality, source ages, confidence.
- Metrics: ingest age per source, model-run duration, number of fires, number of localities with low confidence.
- Alarms to email: model-run error count, API 5xx, any source older than twice its cadence.
- A hidden `/v1/health` returning source ages for the video and for debugging.

## 11. Failure handling

| Failure | Result |
|---|---|
| One source down | Previous cache used; ages shown; confidence lowered |
| All sources down | API serves last LATEST with age; frontend shows the "could not refresh" state |
| Model exception for one locality | Others unaffected; that locality keeps its last good item |
| Bedrock error | Template "why" text used (the P0 text) |
| Open-Meteo rate limit | Back off; no per-user calls so this only affects ingest |

## 12. Cost and rate budget

Per day: winds 4 runs x 121 points (about 500 call units), CAMS 4 x 12, FIRMS 72 calls, OpenAQ about 300 calls (staggered, under 60 per minute). All inside free limits. Replay fetching is a one-off (121 points x one 10-day window x 9 variables). Bedrock calls (P1) are cached by payload hash, at most one per locality per run, and skipped when the hash is unchanged.

## 13. Local development

- Tests run offline on fixtures: saved, trimmed real responses of each source in `backend/tests/fixtures/`.
- Each source client has a `fixtures` mode switched by an environment variable.
- A `scripts/run_local` entry runs the full pipeline on fixtures and writes a payload to disk that the frontend can load as mock data. This lets frontend work start before any AWS deployment.

## 14. Deployment

1. Create AWS account or sandbox, verify student status on Builder Center, enable free tier.
2. Store keys in SSM.
3. `sam build` and `sam deploy --guided` once; commit `samconfig.toml` without secrets.
4. Seed config and run one manual model-run; confirm DynamoDB item and API response.
5. Build the SPA with the API base URL; upload to Amplify Hosting.
6. Add alarms; run the smoke test script against the live URL.
7. Deploy a hello-world route in Phase 0 and keep deploying; do not leave the first real deployment to the last hours.
